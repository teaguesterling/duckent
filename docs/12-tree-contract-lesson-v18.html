PRELUDE

Two tables you already have

DEPLOYED

A family of extensions loads hierarchical data into ordinary DuckDB tables: sitting_duck (ASTs, 27 grammars), webbed (XML/HTML), panduck & duck_block_utils (Markdown, DOCX, PDF). No pointers, no nested types, no document store — rows. Here is the same pattern from two very different producers.

A Markdown file through read_markdown_blocks becomes a block per row: type, nesting level, source order, content — the duck_block table format that duck_block_utils, panduck, and the markdown extension all share. A Python file through sitting_duck becomes a node per row (output schema): type, depth, DFS order — plus native extras like descendant_count — and CSS selectors already query it. Compare the two schemas and the same skeleton appears in both: rows in traversal order, a nesting column, a type column. Everything else — ids, attributes, counts — varies by producer. That shared skeleton is not a coincidence, and taking it seriously is what the rest of this lesson does: first by hand (Lessons 1–3), then as a contract (Lesson 4), then as syntax (Lessons 6–8).

That is also the order the work happened in, and the order is the argument. We started with ASTs and CSS: sitting_duck put selectors on source code, and it worked. Then we went backwards, to where CSS came from — HTML — and brought along everything already modeled as duck_blocks: Markdown, DOCX, PDF, not just HTML, with no conversion to or from HTML at any point. The duck_block tree handled it as it stood. Your documents were rows too. Only then did we ask the question this lesson is organized around: what do ASTs and duck_blocks actually need to be trees, what does CSS need on top of that to have anything to say, and what is there only to make it fast? Those three answers are R, S, and O.

LESSON 2

  
sitting_duck, as it ships

LESSON 3

  
The encoding: a tree as its own traversal

  

    

      

        
Node IDs are depth-first order, so structure is adjacency: anchored at a body block, a documented function is three consecutive rows — block, expression_statement, string — and DuckDB's window machinery reads it (with parentage verified, not just position). First-child is an aggregate: min(node_id) per parent; arg_min(type, node_id) reads its type.

        
This encoding has a name and a history: pre/size/level, from the XML-database era — Grust's XPath accelerator, MonetDB/XQuery's Pathfinder. sitting_duck's node_id / descendant_count / depth is that table column for column, converged on independently. That history pays off directly: DuckDB's recently optimized recursive CTEs (USING KEY, from the same Tübingen group) are about to matter below.

      

      

        
⧉
          
QUALIFY (type,
  lead(type) OVER w,
  lead(type,2) OVER w)
= ('block','expression_statement',
   'string')
AND lead(parent_id) OVER w = node_id

          
The pattern as a row value. Grep scanned adjacent lines; this scans adjacent rows with types — and everything joins.

        

      

    

  






  
LESSON 4 · R

  
Required: what makes rows selectable

  

    

      

        
The selector engine never needed pointer-linked trees. The tree is real; the pointers were optional — what it consumes is rows under three requirements. R1: order matters. R2: a structural basis of level | parent — either one, each derivable from the other. A level column obeys level[n+1] ≤ level[n]+1 (descend at most one, pop freely — that invariant alone characterizes a forest); a parent column derives (order, level) via one recursive CTE, needing only a sibling sort key — without one the source conforms to the sibling-free profile: +, ~, :first-child refused legibly, everything else intact. That's the whole of it: R1 + R2 are the minimal treeness set — everything else in the contract is about what you can say or how fast you can say it. A type accessor isn't required for trees at all, only for CSS-style selection — so it lives in S (as S0°, defaulting every node to type node), and a typeless tree still matches structurally. And R0°, spelled ROOT (col, …), is required iff the relation holds more than one tree: tree-identity columns, constant per tree — delimiting forests, keying tree-granular DML (INSERT OR REPLACE by ROOT = re-derivation; never row surgery), feeding ATTACH. Absent, the relation is one tree; per-tree order resets without ROOT are rejected outright. Accessors may be bare column reads.

LESSON 4 · S

  
Semantics: what selectors can say

  

    

      

        
First, the base slot: S0°, the type accessor — total, defaulting every node to type node, because selection needs a type dimension even when trees don't; declare TYPE and type selectors light up. S is the expressive surface: id accessors (#main), classes (.fn), and attributes in two tiers — named accessors, declared per attribute and typed (numeric and date operators live here; [start_line>100] needs a real INT), and a map catch-all for the long tail, string ops only. Named wins; the map serves undeclared names; neither declared → refused legibly. Rule of thumb: hot attributes earn names; the map is for the tail, not the hot path. And the extension mechanism: custom pseudo-classes as pure SQL macros — the macro is the semantics — with per-tree binding: a tree declares its pseudo map (or a prefix), shadowing a shared sel_* library tier, so :docblock can mean the right structure per grammar without collision. The pseudo name is the method, the tree is the type, the macro is the instance — and ambiguity is refused at registration, not discovered at match time. Some predicates are just named selectors: :docblock is a macro whose body is itself a selector, which is where grammar-specific structure goes to hide behind one portable name.

LESSON 4 · O

  
Optimizations: cost only, never results

  

    

      

        
O accessors buy speed: the non-native basis member, subtree size, child count, next sibling (pre+size+1). Each has a default derivable from (order, level); native columns register as overrides — and every override must test-equal its default. An override that changes a match set is not a fast path; it is a corrupted encoding, flagged at that severity.

        
The refinement that turns this from rule into theory: the R/O split has a criterion. Type, id, classes are row-local — they depend on nothing but the row. Every O member is row-transcendent: its value summarizes other rows, and that dependence is exactly what scopes it. O values are namespaced to (taxon, load-watermark) — valid within their own tree's materialized extent, never across an attachment splice (a parent tree's descendant_count cannot see attached forests), never above an unloaded frontier. A namespace-checked read yields a Bound; a mismatched read yields an Estimate — estimates may inform join order, never results. The XML era fought this as the dynamic-update problem and answered with renumbering; the contract answers with locality.

        
CASE STUDY · WHY duck_blocks SHIPS NO O
sitting_duck stores parent ids and descendant counts natively; duck_block_utils stores neither — and both are right. ASTs are deep (one function can be hundreds of nodes) and queried structurally, so O pays daily. Document blocks are bigger, flatter, and spliced constantly — assembled, sliced, concatenated — and id-free, O-free rows compose by concatenation; O columns would be perpetually stale under that splice rate. Omitting O isn't a gap. It's the correct point on the depth × splice-rate tradeoff, and the contract holds both ends.

LESSON 4 · W

  
World: linking trees without touching them

  

    

      

        
Trees link to other trees, and the linkage has laws. W1: attachments are root-restricted foreign keys — child-tree roots reference parent-tree nodes, interior nodes never do (that restriction keeps ancestry a forest, not a graph), and the child root splices in at level(parent)+1. W2: loaders — demand materialization with a tri-state frontier (loaded / unloaded / absent; the distinction matters). Both are parent-parameterized: bindings are deterministic functions of the parent row's local columns — a code fence's language attr selecting the parser is the archetype. W3: epoch manifests, provenance keyed by (parent, params), refresh by selector.

        
The governing law, W-locality: within-tree match sets are invariant under any change to W. Attach, detach, load, refresh — a single tree's answers never move. W belongs to binding, planning, and provenance; never to semantics. And dangling references are drift telemetry, not errors: absence at a frontier is a fact.

Now read the four block letters back. We taught them in dependency order — R structure, S speech, O speed, W world — because each stratum leans only on the ones before it. Rearrange the initials and they spell the contract's name: ROWS — Required, Optimizations, World, Semantics. Nobody planned the acronym; it was found — which is how you know the factoring is right.

LESSON 6

  
duckent I — CREATE TREE: speaking Tree, fluently

  

    
EXPERIMENTAL

    

      

        
DuckDB 2.0's runtime-extensible PEG parser lets extensions add syntax and reuse the rest of SQL — so the ROWS contract becomes DDL. The shape specification is the contract, slot for slot, and it scales from two lines to full dress. Minimal: one slot makes rows a tree — type defaults to node, so * and every structural combinator already work. Typical: an abstract tree (SHAPE ONLY — required whenever there's no AS, so sourcelessness is declared intent, never an accident) instantiated with LIKE, which copies semantics, never source — the universal LIKE contract. Full dress adds the S tiers and O declarations.

        
Read the full-dress figure as a tour of the blocks: ROOT is tree identity (R0); LEVEL/TYPE the required basis; ATTR the named/typed tier (bulk-bindable via COLUMNS('a_(.*)') AS '\1') over an ATTRS MAP catch-all; PSEUDO binds pseudo-classes per tree — the value is an ordinary expression in the tree's row scope, exactly like a generated column or CHECK constraint, so calling a macro is just calling it: docblock := has_docblock(file_path, node_id). No lambda syntax, no binding machinery — SQL already knows how to evaluate an expression per row. A PSEUDO PREFIX pulls in a whole shared library, shadowed by anything tree-local. And every OPTIMIZE annotation auto-generates its conformance assertion: an O override that diverges from its derivable default is flagged as corruption, not speed. Miss a capability and the refusal is legible at bind time: "tree org declares no CLASSES accessor."

      

      

        
⧉
          
-- minimal: one slot makes a tree
CREATE TREE toy (LEVEL depth)
  AS FROM read_csv('toy.csv');

-- typical: abstract shape + instance
CREATE TREE sitting_duck_ast (
  SHAPE ONLY,
  ROOT (file_path),
  LEVEL depth,
  TYPE  semantic_type_to_string(
          semantic_type),
  ATTR  (name := name,
         start_line := start_line),
  PSEUDO PREFIX 'sel_ast_'
);
CREATE TREE code LIKE sitting_duck_ast
  AS FROM read_ast('src/**/*.py');

          
          
SHAPE ONLY declares abstractness; LIKE instantiates. Semantics copy; source never does.

        

        
⧉
          
-- full dress: the whole contract
CREATE TREE full (
  SHAPE ONLY, ROOT (file_path),
  LEVEL depth, TYPE t, ID name,
  CLASSES classes,
  ATTR (COLUMNS('a_(.*)') AS '\1'),
  ATTRS MAP extra,
  PSEUDO (leaf := descendant_count = 0,
  docblock := has_docblock(
    file_path, node_id)),
  PARENT parent_id       OPTIMIZE,
  SIZE descendant_count  OPTIMIZE
);

          
Every OPTIMIZE ships its own conformance test. Named attrs are typed; the map is string-only.

        

      

    

  






  
LESSON 7

  
duckent II — MATCH, and the query it abstracts

  

    
EXPERIMENTAL

    

      

        
Think of MATCH as Lesson 3, automated. The selector compiles into exactly the machinery you hand-wrote there — the QUALIFY windows, the grouped firsts, the anti-joins — generated against whatever a tree's shape declares. That's what "abstracts sitting_duck" means precisely: sitting_duck's ast_select is the special case where the basis is level, the O columns are native, and the vocabulary is the code taxonomy; MATCH is the same compilation, parameterized by any shape. Semantics consult declarations — R, S, and attachments — never state, so the answers can't depend on caches or load timing.

        
And the two bases earn their existence here. Level basis is what a producer emits when it already walks the structure — a parser streams DFS order and depth for free, which is why sitting_duck stores node_id/depth/descendant_count natively (pre/size/level: deep trees, structural queries daily, so the O columns are worth storing). Parent basis is how the world's data already sits — every org chart and category table is an adjacency list — and the recursive CTE that DFS-numbers it (fast under USING KEY) is the encoder. You can write it once to understand it; then the DDL internalizes it and you never write it again.

      

      

        
⧉
          
FROM code
MATCH '.fn:not(:has(:docblock))'
SELECT name, start_line;
-- compiles to rung 0's shape:
-- windows, firsts, ANTI JOIN

-- ad hoc, no CREATE needed:
FROM 'code.parquet'
USING TREE sitting_duck_ast
MATCH '.fn:not(:has(:docblock))';

          
          
MATCH over a created tree, or USING TREE over a bare source — same compiler, USING SAMPLE-style modifier.

        

        
⧉
          
-- adjacency, by hand (the encoder):
WITH RECURSIVE org AS (
  …DFS numbering over manager_id,
   ordered by hire_date… )
-- adjacency, internalized:
CREATE TREE org (
  PARENT manager_id,
  SIBLING ORDER (hire_date),
  TYPE role, ID email
) AS FROM employees;

FROM org
MATCH 'manager:has(> engineer)'
SELECT id;

          
The recursive CTE vanishes into the DDL. Level when the producer walks; parent when the data already sits that way; each derives the other.

        

      

    

  






  
LESSON 8

  
duckent III — MATCH ∘ SQL: one pipeline, one host door

  

    
EXPERIMENTAL

    

      

        
MATCH is a clause, not a function. Bare, it flows straight into the pipeline you already know — FROM … USING TREE … MATCH … SELECT … WHERE … GROUP BY — terminated by the next clause keyword, scanned outside balanced brackets. No outer string literal, so quote-doubling dissolves. And because the shape projection is the matcher's view, not the result type, MATCH emits raw rows: the WHERE after it is ordinary SQL filtering on everything the source knows, no attribute macros required.

        
When attribute operators run out — subqueries, BETWEEN, real expression trees — SQL does not go into CSS. CSS stays wholly portable: it extends by pseudo-classes, and minting one is a declaration, not a hack — PSEUDO (busy := child_count > 2) and :busy exists. The host door is a second language on the same matcher: MATCH USING TREEQL, one step per line, each a combinator keyword plus parenthesized clauses whose keywords are the S slots — TYPE, ID, CLASS, ATTR, PSEUDO — plus a native WHERE that is arbitrary SQL against that step's projection row (closed shapes still refuse undeclared columns: power added, visibility unchanged). AS y names a step, and a named step is a joined alias you can read dotted in the SELECT after the match. The boundary doctrine, quoted in every refusal: CSS extends by pseudo-classes; TREEQL integrates the host; never both in one language.

        
One last collision, from our own toolchain: the taxonomy's 28th grammar is SQL itself, whose trees contain select nodes. Keyword-typed selectors quote like identifiers — MATCH "select" > "from" — and the pipeline keeps flowing. And TREEQL is more than language number two: every registered language normalizes to it, EXPLAIN MATCH prints it, and cross-language differentials compare its normal forms.

      

      

        
⧉
          
-- bare MATCH, in the pipeline
FROM code USING TREE sitting_duck_ast
MATCH .fn:not(:has(:docblock))
SELECT name, start_line
WHERE  file_path LIKE 'src/%'
GROUP  BY ALL;

          
          
The next clause keyword ends the pattern. WHERE after MATCH filters matched rows — raw columns, typed, macro-free.

        

        
⧉
          
-- the host door: TREEQL, step WHERE is native
FROM code
MATCH USING TREEQL
           (TYPE 'function_definition') AS f
CHILD      (TYPE 'block')
DESCENDANT (WHERE name IN (SELECT f FROM flagged)) AS y
SELECT f.name, y.start_line;

          
One step per line; clause keywords are the S slots; WHERE is SQL against the step's own projection row. Captures are joined aliases.

        

        
⧉
          
-- css has no host escape: mint a pseudo-class
CREATE TREE code LIKE ast
  (SHAPE ONLY, PSEUDO (busy := child_count > 2));
FROM code MATCH .fn:busy SELECT name;

FROM code MATCH .fn[WHERE x > 2]   -- ✗ refuses:
-- css has no host escape — mint a PSEUDO,
-- or MATCH USING TREEQL

MATCH "select" > "from"  -- 28th grammar

          
Two languages, one matcher. The refusal names the routing; keyword types quote like identifiers.

        

      

    

  






  
LESSON 9

  
duckent IV — forests, attachments, virtual worlds

  

    
EXPERIMENTAL

    

      

        
Forests and DML. ROOT makes DML tree-granular: append trees, drop trees by key, and INSERT OR REPLACE is re-derivation — re-parse a file, replace its tree, epoch bumps. Within-tree row surgery doesn't exist; the 2004 renumbering problem is answered by granularity: renumbering never crosses a partition you didn't wholly replace.

        
Attachments. Trees link by root-restricted foreign key — child roots reference parent nodes, interior nodes structurally can't (their only cross-tree coordinate is ROOT, constant per tree) — splicing in at level(parent)+1, with bindings that are deterministic functions of the parent row: a code fence's language attr selecting the parser is the archetype. The first thing attachments buy is ontology mapping: shared reference trees — NCBI's tree of life, WordNet, HS tariff codes — attached many-to-one, every row that names a concept keying into one taxonomy, with subtree membership as a pseudo-class; if you've ever shipped a closure table, you already built that tree's O-block. The second is the analytics workhorse, hierarchy × facts: every subtree rollup today is the same three-part boilerplate — recursively collect descendant ids, semi-join the fact table, aggregate — rewritten per hierarchy, per question. Attach the facts to the tree once and the boilerplate becomes one selector plus one aggregate. (Chains extend arbitrarily far — network to service to file to AST — each boundary a loader; the details are in the field guide.)

        
Virtual trees. Trees too large to materialize whole: materialize two levels, load branches on demand — selector pushdown decides which branches, unloaded is distinct from absent, and matching must equal the fully-materialized ideal within the selector's scope (so demand loading is an evaluation strategy, never a semantics change). Refresh is by selector; every load carries an epoch manifest.

      

      

        
⧉
          
-- forest DML, by ROOT
INSERT INTO code
  FROM read_ast('new.py');
DELETE FROM code
  WHERE file_path = 'old.py';
INSERT OR REPLACE INTO code
  FROM read_ast('mod.py');

          
          
Tree-granular; OR REPLACE = re-derivation by key. Never row surgery.

        

        
⧉
          
-- example 1: ontology mapping
ATTACH ncbi_taxa TO samples.organism
  USING (taxon_id);

FROM samples
MATCH 'sample[tissue="liver"]
       organism:isa("Mammalia")'
SELECT sample_id;
-- :isa = closure-table lookup:
-- the reference tree's O, precomputed

          
Example 1 — a shared taxonomy, attached many-to-one; the selector crosses from your rows into the ontology and back.

        

        
⧉
          
-- example 2: subtree rollup
-- (today: recursive CTE + join + agg,
--  rewritten per hierarchy, per question)
ATTACH ledger TO coa.account
  USING (account_id);

FROM ledger
MATCH 'account#opex *
       entry[fy="2026"]'
SELECT sum(amount);

          
Example 2 — chart-of-accounts × ledger: "spend under opex" as one selector. Works identically for categories × sales, org × headcount, BOM × costs — the community's canonical clunky-CTE cases.

        

        
⧉
          
CREATE VIRTUAL TREE fs (…)
  MATERIALIZE TO DEPTH 2
  LOAD FROM fs_scan(:parent);

REFRESH TREE fs BRANCH 'dir#var';

          
Two levels resident, branches on demand, refresh by selector. Unloaded ≠ absent.

        

      

    

  






  
LESSON 10

  
duckent V — what's built, what's next

  
The first three milestones now run as a macro prototype on DuckDB 1.5.5. Here is what exists, what building it proved, and where the next line of code goes.

  

    
EXPERIMENTAL

    

      

        
As of this revision, M0, M1, and M1½ run. The duckent repository holds them as SQL macros under sql/: a catalog of shapes and trees, the projection compiler onto the canonical columns, both basis derivations, forest DML with P13 checked on ingest, and a TREEQL match compiler with captures. Every mutating operation is a pure tree_compile_* macro that returns SQL text; a small Python runner executes it today, a bound table function will in the extension. Eleven sqllogictest files pass and nine planted mutants die, and the same .test files are meant to run unchanged against the C++ build.

        
Building it settled things the design could not. The derived _parent and _size equal sitting_duck's native parent_id and descendant_count on every row of both parquet fixtures, which is the O law holding on real data. DuckDB's query() refuses text from any macro whose body contains a SELECT, which is why the compilers that must read the catalog are executed by the runner rather than fed to it. A partitioned row_number() without ORDER BY does not preserve scan order, so frozen order captures the scan sequence first. And the harness did its job: two mutants survived their first run, and the answer was a multi-root test and a re-scoped mutant, never a manifest edit.

        
The review that gated the merge found the defect the tests had not: tree_ddl_alter rebuilt a tree from its create-time source and silently dropped every partition ingested since. It now refuses, naming the partitions and the way around. That is doctrine 3 and doctrine 4 in one finding, and it is the kind of thing the FINDINGS file exists to record.

The C++ port replaces the derivations' recursive CTEs with one stack walk over pre-order, which is what "a tree is its own traversal" means operationally. The macro bridge: what MATCH compiles to, running today
Pre-2.0, the whole DDL compiles to two table macros. A shape is a projection macro onto canonical columns (_root, _pre, _level, _type, _id, _size, …). MATCH generates its query against those columns and nothing else. Below is the flagship selector compiled by hand exactly the way the compiler will emit it, run against the prelude's app.py on DuckDB 1.5.5 with sitting_duck.
LOAD sitting_duck;
CREATE TABLE app AS FROM read_ast('app.py');

-- a SHAPE compiles to a projection macro onto canonical columns
CREATE MACRO shape_ast(src) AS TABLE
  SELECT file_path AS _root, node_id AS _pre, depth AS _level,
         semantic_type_to_string(semantic_type) AS _type, name AS _id,
         descendant_count AS _size, parent_id AS _parent,
         (flags & 6) = 6 AS is_def,          -- ATTR: binds a name as a DEFINITION
         type AS node_type, start_line
  FROM query_table(src);

-- MATCH '.fn:not(:has(:docblock))' compiles against the canonical columns only
CREATE MACRO match_fn_without_docblock(src) AS TABLE
  WITH n AS (FROM shape_ast(src)),
  docblock AS (   -- :docblock = block > expression_statement:first-child > string:first-child
    SELECT b._pre, b._size FROM n b
    JOIN n e ON e._parent = b._pre AND e._pre = b._pre + 1   -- first child: next row in pre-order
    JOIN n s ON s._parent = e._pre AND s._pre = e._pre + 1
    WHERE b.node_type = 'block' AND e.node_type = 'expression_statement' AND s.node_type = 'string')
  SELECT f._id AS name, f.start_line
  FROM n f
  WHERE f._type = 'DEFINITION_FUNCTION' AND f.is_def          -- .fn
    AND NOT EXISTS (FROM docblock d                         -- :not(:has(…)) over the pre/size range
                    WHERE d._pre BETWEEN f._pre + 1 AND f._pre + f._size);

FROM match_fn_without_docblock('app');

-- the encoder: parent basis -> (order, level); sibling key = hire_date
WITH RECURSIVE walk USING KEY (email) AS (
  SELECT email, role, manager_email, 0 AS level,
         [row_number() OVER (ORDER BY hire_date, email)] AS path
  FROM employees WHERE manager_email IS NULL
  UNION ALL
  SELECT e.email, e.role, e.manager_email, w.level + 1,
         w.path || [row_number() OVER (PARTITION BY e.manager_email ORDER BY e.hire_date, e.email)]
  FROM employees e JOIN walk w ON e.manager_email = w.email
)
SELECT row_number() OVER (ORDER BY path) - 1 AS node_id,
       level, role AS type, email AS id, manager_email AS parent
FROM walk ORDER BY node_id;

TREEQL: a keyword match language isomorphic to the S block
One step per line, each a combinator keyword plus parenthesized predicate clauses. The clause keywords are the slot names, so declaration and query speak the same words: CREATE TREE … TYPE kind on one side, (TYPE 'fn') on the other.
clauseslotnotes

ATTR start_line > 100S3full SQL comparison operators over declared attributes; portable despite the operator richness, because the portability boundary is declared-attrs versus arbitrary expressions, not operator poverty
PSEUDO 'leaf'S4repeatable
WHERE <expr>the host doorarbitrary row-scope SQL, compiled against the step's projection view, never the raw relation (MN19 lives here now). The system's only host door.
grammar sketch; the first step takes no combinator (D-N12), like the first FROM item
match_treeql := 'MATCH' 'USING' 'TREEQL' step+
step         := combinator? '(' clause (',' clause)* ')' ('AS' ident)?
              | combinator                          -- bare step = any node
combinator   := 'CHILD' | 'DESCENDANT' | 'SIBLING'  -- SIBLING = adjacent (+)
clause       := 'TYPE' expr | 'ID' expr | 'CLASS' expr
              | 'ATTR' comparison | 'PSEUDO' expr | 'WHERE' expr
Semantics by desugaring: each step is a join against the same projection; the combinator compiles to a structural predicate over the basis (CHILD: parent equality; DESCENDANT: the pre/size range; SIBLING: adjacency under the same parent). Clauses compile to S-accessor predicates. Bare-safe by construction: every step opens with a keyword or a parenthesis, so no token collides with clause-keyword termination.
Worked example, and where CSS stops
FROM code
MATCH USING TREEQL
           (TYPE 'node')
CHILD      (ID 'parse_ast')
DESCENDANT (CLASS 'fn')
SIBLING    (ATTR start_line > 100)
CHILD      (PSEUDO 'first-child', PSEUDO 'leaf')
SIBLING    (WHERE child_count > 2)
CHILD      (CLASS 'if', WHERE child_count BETWEEN 4 AND 8) AS y
DESCENDANT (TYPE 'x')
CHILD
SELECT y.name
WHERE  something > 1
The first five steps have an exact CSS spelling: node > #parse_ast .fn + [start_line>100] > :first-child:leaf. The three WHERE steps have none, and that is the point: CSS is the portable, corpus-rich surface (browser muscle memory, Text-to-ASTCSS), TREEQL is the one that can afford a ten-line pattern and a host predicate. Result-set WHERE, SELECT, and GROUP BY follow bare, unambiguous because a step-level WHERE is always parenthesized.

The canonical-form role
Every registered language normalizes to TREEQL. EXPLAIN MATCH prints it, so a plan has one human-readable spelling. Cross-language equivalence (P22) compares TREEQL normal forms instead of pairwise fixtures. The lesson's "selector → window functions" compilation gains its middle rung: CSS → TREEQL → SQL. And a second constrained-decoding target sits beside CSS: no phrasebook, but a grammar so SQL-shaped the constraint is cheap. MN24 guards the whole arrangement: lang → TREEQL → plan must equal lang → plan, or EXPLAIN lies.
